> 버전: v0.1 · 작성일: 2026-09-28

# DECISIONS

## D-1 · 전용 pywebview 애플리케이션으로 작성

**선택**

Windows용 YouTube Downloader를 `pywebview` 기반의 독립 애플리케이션으로 작성한다.

**근거**

- Python으로 제공되는 기존 다운로드 기능을 애플리케이션 내부에서 직접 사용할 필요가 있다.
- 이번 앱은 단일 목적의 데스크톱 유틸리티이며, 필요한 화면 구조가 비교적 작다.
- Python backend와 HTML/CSS/JavaScript 기반 UI를 한 앱 안에서 연결하기에 적합하다.

**배제한 대안**

- `workbench-kit`의 pywebview shell을 기반으로 파생하는 방식: YouTube Downloader에 필요하지 않은 Activity Bar, Explorer, Editor 계층, 분할 화면 등 공통 shell의 범위가 커서 배제한다.
- Electron 기반 독립 앱: Python backend를 내장해 사용하는 이번 요구에서는 별도의 프로세스/브리지 구성이 늘어나므로 우선 선택하지 않는다.

---

## D-2 · 다운로드 기능은 기존 youtube-kit을 재사용

**선택**

영상/재생목록 정보 조회와 영상·음성·자막 다운로드는 로컬에 있는 `youtube-kit`을 backend 기능으로 사용한다.

**근거**

- `youtube-kit`에 영상 및 재생목록 정보 조회 기능이 이미 존재한다.
- 영상과 음성 포맷을 ID로 지정하는 기능, 자막 트랙 선택 기능, 진행 이벤트와 취소 기능이 이미 제공된다.
- GUI 프로젝트에서 동일한 다운로드 로직을 다시 구현하면 기능 중복과 유지보수 지점이 늘어난다.

**배제한 대안**

- GUI 프로젝트가 `yt-dlp`를 직접 호출해 다운로드 규칙을 별도로 구현하는 방식: `youtube-kit`과 책임이 중복되고 두 프로젝트의 동작 차이가 생길 수 있어 배제한다.
- 기존 `youtube-kit` 코드를 GUI 저장소로 복사하는 방식: 원본과 사본이 분기될 수 있으므로 배제한다.

---

## D-3 · workbench-kit은 UI 스타일 참고용으로만 사용

**선택**

로컬 `workbench-kit`에서 Light/Dark 테마 구성 방식, VS Code 계열의 간결한 색상 감각, spacing, 아이콘 사용 방식, pywebview와 frontend 연결 사례를 참고한다. 코드 구조나 shell 자체에 의존하지 않는다.

**근거**

- 사용자가 이미 익숙한 UI 감각을 재사용할 수 있다.
- shell의 불필요한 기능을 가져오지 않고도 시각적 일관성은 유지할 수 있다.
- Downloader의 화면은 작업 큐 중심으로 훨씬 단순하게 유지할 수 있다.

**배제한 대안**

- `workbench-kit`을 패키지 또는 base shell 의존성으로 추가하는 방식: 필요하지 않은 기능과 결합도가 증가하므로 배제한다.
- `workbench-kit`의 전체 레이아웃을 그대로 복제하는 방식: Downloader의 단일 목적 화면에 과도하므로 배제한다.

---

## D-4 · 테마는 Light와 Dark 두 개만 제공

**선택**

v0.1의 테마는 Light와 Dark 두 개만 제공한다.

**근거**

- 사용자가 요구한 범위가 두 테마로 명확하다.
- 테마 수를 제한하면 시각적 일관성과 유지보수가 단순해진다.
- 앱의 핵심은 테마 다양성이 아니라 다운로드 큐의 가독성과 조작이다.

**배제한 대안**

- 다수의 색상 테마 또는 사용자 정의 테마: v0.1의 목적에 필요하지 않고 스타일 검증 범위를 넓히므로 배제한다.
- OS 테마에만 자동 추종하고 수동 전환을 제공하지 않는 방식: Light/Dark를 명시적으로 사용할 수 있어야 하므로 배제한다.

---

## D-5 · 아이콘은 Codicon 계열 스타일로 통일

**선택**

주요 툴바 조작과 상태 표현에 Codicon을 사용해 VS Code와 유사한 작고 단순한 아이콘 스타일을 유지한다.

**근거**

- `workbench-kit`에서 참고하려는 시각 방향과 잘 맞는다.
- 텍스트 버튼을 반복하는 것보다 좁은 공간에서 조작을 간결하게 배치할 수 있다.
- 툴팁과 조합하면 의미를 유지하면서 화면 밀도를 낮출 수 있다.

**배제한 대안**

- 여러 아이콘 라이브러리를 섞어 사용하는 방식: stroke, 크기, 정렬 감각이 달라져 일관성이 깨지므로 배제한다.
- 모든 조작을 큰 텍스트 버튼으로 표시하는 방식: 테이블 중심의 compact UI와 맞지 않아 배제한다.

---

## D-6 · 메인 화면은 테이블형 다운로드 큐를 중심으로 구성

**선택**

앱의 주 작업 영역은 영상 하나가 한 행을 차지하는 테이블형 다운로드 큐다.

**근거**

- 여러 영상의 설정과 상태를 동시에 비교하기 쉽다.
- 토렌트/다운로드 매니저와 유사한 작업 모델이 여러 항목의 대기·진행·완료를 관리하기에 적합하다.
- 해상도·코덱·음성·자막 같은 항목별 선택을 행 안에 배치할 수 있다.

**배제한 대안**

- 영상마다 큰 카드를 사용하는 UI: 항목 수가 늘어날수록 한 화면에서 비교 가능한 개수가 적어져 배제한다.
- 상세 설정 화면을 매 영상마다 별도 창으로 여는 UI: 반복 조작이 많아지고 전체 큐 비교가 어려워 배제한다.

---

## D-7 · URL 붙여넣기를 큐 추가의 주 동작으로 사용

**선택**

클립보드의 YouTube URL을 URL 입력 영역에 붙여넣으면 별도의 `Analyze` 단계를 요구하지 않고 큐에 추가한다. 큐에 추가된 뒤 정보 조회 결과로 행을 자동 갱신한다.

**근거**

- 사용자가 원하는 기본 흐름이 `URL 복사 → 붙여넣기 → 큐 추가`다.
- 큐 등록과 정보 조회를 한 사용 흐름으로 묶으면 반복 작업 단계가 줄어든다.
- 정보 조회가 끝나기 전에도 사용자는 항목이 접수됐음을 바로 확인할 수 있다.

**배제한 대안**

- URL 입력 후 별도의 `Analyze` 버튼을 눌러야 큐에 들어가는 2단계 흐름: 반복 작업이 늘어나므로 배제한다.
- 정보 조회가 모두 끝난 뒤에만 행을 생성하는 방식: 네트워크 응답 동안 사용자가 입력이 접수됐는지 확인하기 어려워 배제한다.

---

## D-8 · 재생목록은 전체 영상을 개별 큐 행으로 펼친다

**선택**

재생목록 URL이 입력되면 재생목록의 전체 항목을 영상 단위의 개별 행으로 큐에 추가한다.

**근거**

- 각 영상의 해상도·코덱·음성·자막을 독립적으로 선택해야 한다.
- 각 영상을 독립적으로 재정렬하고 진행 상태를 확인할 수 있다.
- 일반 영상과 재생목록 영상이 동일한 큐 모델을 공유하게 된다.

**배제한 대안**

- 재생목록 전체를 하나의 행으로 유지하는 방식: 개별 영상 설정과 순서 변경이 어려워 배제한다.
- 재생목록 전용 별도 화면을 만드는 방식: UI와 상태 모델이 이중화되므로 배제한다.

---

## D-9 · 영상별 미디어 선택은 큐 행에서 직접 수행

**선택**

각 큐 행에 해상도, 영상 코덱, 음성, 자막 선택 컨트롤을 둔다. 선택 목록은 해당 영상에서 실제 조회된 선택지로 구성한다.

**근거**

- 여러 영상의 설정을 한 화면에서 비교·수정할 수 있다.
- `youtube-kit`의 포맷/트랙 선택 모델과 직접 대응된다.
- 별도 설정창을 반복해서 열지 않아도 된다.

**배제한 대안**

- 선택 행의 하단 상세 패널에서만 포맷을 고르는 방식: 여러 영상 설정을 비교하기 어려워 배제한다.
- 앱이 포맷을 항상 자동 결정하고 사용자가 선택하지 못하게 하는 방식: 사용자가 영상별로 선택하려는 요구와 맞지 않아 배제한다.

---

## D-10 · 큐 순서는 위/아래 이동으로 조정

**선택**

선택한 행을 명시적인 위/아래 이동 조작으로 재정렬한다.

**근거**

- 사용자가 요구한 동작이 명확하다.
- 드래그 앤 드롭보다 구현과 사용 규칙이 단순하다.
- 키보드 또는 작은 Codicon 버튼과 자연스럽게 연결할 수 있다.

**배제한 대안**

- v0.1에서 드래그 앤 드롭만 제공하는 방식: 정밀한 이동과 키보드 사용이 불편할 수 있고 필수 요구가 아니므로 배제한다.
- 큐 순서를 고정하는 방식: 사용자가 다운로드 순서를 직접 조정할 수 없으므로 배제한다.

---

## D-11 · 정보 조회와 다운로드는 UI를 막지 않게 처리

**선택**

영상 정보 조회 및 실제 다운로드가 진행되는 동안 큐 UI는 계속 표시·조작 가능해야 하며, 작업 결과는 해당 행의 상태와 진행 정보로 반영한다.

**근거**

- 재생목록은 여러 영상의 정보를 연속해서 조회해야 하므로 동기적으로 화면을 막으면 사용성이 크게 떨어진다.
- 다운로드 중에도 다른 큐 항목의 설정과 상태를 확인할 필요가 있다.
- `youtube-kit`이 진행 이벤트를 제공하므로 행 단위 상태 갱신에 사용할 수 있다.

**배제한 대안**

- 메타데이터 조회나 다운로드가 끝날 때까지 전체 UI 입력을 차단하는 방식: 큐 기반 앱의 목적과 맞지 않아 배제한다.

---

## D-12 · 초기 화면 구조는 Toolbar + URL + Queue Table + Status 영역으로 제한

**선택**

v0.1의 항상 보이는 핵심 화면은 상단 툴바, URL 입력 영역, 중앙 큐 테이블, 하단 상태 요약 영역으로 구성한다.

**근거**

- 현재 요구를 모두 담으면서도 화면 구조가 단순하다.
- `workbench-kit`과 달리 별도의 Activity Bar, Explorer, Editor 영역이 필요하지 않다.
- 큐가 화면의 중심이라는 프로젝트 의도가 분명해진다.

**배제한 대안**

- 좌측 사이드바와 다중 패널을 기본으로 항상 표시하는 구조: v0.1에서 사용하지 않는 영역이 늘어나므로 배제한다.
- 영상별 상세 패널을 항상 고정 표시하는 구조: 핵심 테이블의 가용 공간을 줄이므로 기본 구조에서 배제한다.

---

## D-13 · 다운로드는 전체 시작 후 큐 순서대로 1개씩 실행

**선택**

툴바의 시작 조작 하나로 다운로드를 시작하며, 받을 준비가 된 행을 큐의 위에서부터 한 번에 하나씩 받는다.

**근거**

- 큐 순서 변경(D-10)이 곧 다운로드 순서가 되어 순서 조작에 의미가 생긴다.
- `youtube-kit`의 순차 처리 방식과 맞고, 진행 표시·취소·실패 처리가 단순하다.

**배제한 대안**

- 전체 시작 후 동시 N개: 진행 표시·취소·실패 처리가 복잡해지고, 큐 순서가 시작 순서라는 뜻으로만 남으므로 배제한다.
- 행별 시작만 제공: 재생목록처럼 행이 많으면 행마다 시작해야 하므로 배제한다.
- 붙여넣으면 자동 시작: 행별로 선택을 확인·조정할 시간이 없어 INTENT의 "사용자가 확인하고 선택"과 부딪히므로 배제한다.

---

## D-14 · 저장 위치는 앱 전체에 한 폴더

**선택**

저장 위치는 앱 전체에 한 폴더이며 툴바에서 바꾼다. 바꾼 위치는 다음 실행 때도 기억한다. 초기값은 사용자의 Downloads 폴더다.

**근거**

- 한 번 정하면 반복 작업마다 다시 고를 필요가 없다.
- 테이블에 저장 위치 열을 두지 않아 compact한 화면을 유지한다.

**배제한 대안**

- 시작할 때마다 폴더 선택: 매번 한 단계가 늘어나므로 배제한다.
- 행별 저장 폴더: 테이블 열이 늘고 v0.1 범위에 비해 과하므로 배제한다.
- 바꿀 수 없는 고정 폴더: 사용자가 저장 위치를 정할 수 없으므로 배제한다.

---

## D-15 · 저장 폴더 안에 영상 ID별 폴더를 두고 meta 파일도 그 안에 저장

**선택**

영상 하나의 결과는 `<저장 폴더>\<영상 ID>\`에 모은다. 정보 조회로 생기는 `<영상 ID>.meta.json`과 받은 영상·음성·자막 파일이 모두 이 폴더에 저장된다. 재생목록에서 펼친 영상도 개별 영상과 같이 저장 폴더 바로 아래의 영상 ID 폴더에 저장한다. 재생목록 조회로 생기는 `<list-id>.playlist.json`은 `<저장 폴더>\<list-id>\`에 둔다.

**근거**

- 영상 하나에 딸린 파일(meta·영상·음성·자막)이 한 곳에 모여 저장 폴더가 어지러워지지 않는다.
- 영상 ID는 항상 유일하고 `youtube-kit`의 파일명 규칙과 같아, 제목의 특수문자·길이 문제가 없다.
- 어디서 넣었든 같은 영상은 한 폴더라 중복 저장이 생기지 않는다.

**배제한 대안**

- 앱 전용 캐시 폴더에 meta 파일 저장: 사용자가 meta 파일을 받은 파일 곁에 두기를 원하므로 배제한다.
- 저장 폴더에 모든 파일을 평면으로 저장: 영상 수가 늘면 파일이 뒤섞이므로 배제한다.
- 폴더 이름을 제목 또는 제목+ID로: 금지 문자 치환·길이 자르기 규칙이 필요하고 제목이 바뀔 수 있으며, 제목만 쓰면 충돌하므로 배제한다.
- 재생목록 폴더 안에 영상별 폴더: 같은 영상을 따로 넣은 적이 있으면 두 곳에 따로 받게 되므로 배제한다.

---

## D-16 · 정보 조회 직후 기본 규칙으로 미리 선택

**선택**

정보 조회가 끝나면 앱 설정의 기본 규칙을 행마다 적용해 해상도·코덱·음성·자막을 미리 선택해 보여 주고, 사용자는 행별로 바꿀 수 있다. 규칙에 맞는 포맷이 없으면 다른 포맷으로 대체하지 않고 그 칸을 비워 둔다. 기본 규칙의 초기값은 "호환 우선"이다 — 영상은 1080p 이하 중 최고 해상도·avc1·높은 fps, 음성은 원본 언어이고 drc가 아닌 m4a 중 최고 음질, 자막은 없음. 기본 규칙은 설정에서 바꿀 수 있다.

**근거**

- 재생목록처럼 행이 많아도 행마다 모든 칸을 고르지 않고 바로 받을 수 있다.
- 미리 선택한 값이 화면에 보이고 사용자가 바꿀 수 있어 INTENT의 "사용자가 확인하고 선택"을 지킨다.
- 규칙에 맞지 않으면 비워 두므로 임의 대체 금지(NFR-6)를 지킨다.
- "호환 우선" 결과는 mp4로 묶여 대부분의 기기에서 재생된다.

**배제한 대안**

- 모든 칸을 비워 둠: 재생목록 100개면 400칸을 골라야 하므로 배제한다.
- 비워 두고 여러 행에 일괄 적용 제공: 행마다 가능한 포맷이 달라 맞지 않는 행이 비어 남으므로 배제한다.
- 규칙 없이 항상 최고 품질 자동 선택: 코덱 호환을 고려하지 않으므로 배제한다.
- 초기 규칙 "품질 우선"(코덱 무관 최고 해상도·음질): 결과가 대개 mkv가 되어 일부 기기에서 재생되지 않으므로 초기값에서 배제한다.
- 초기 규칙 "음성 우선"(영상 없음): 영상 다운로드가 기본 흐름이므로 초기값에서 배제한다.

---

## D-17 · 영상·음성·자막 칸에 `없음`을 허용

**선택**

영상·음성·자막 세 칸 모두 `없음`을 고를 수 있다. 영상이 `없음`이면 음성만 받고(`youtube-kit` `audio()`), 영상과 음성이 모두 `없음`이면 자막만 받는다(`subtitle()`). 단, 영상 칸이 선택되어 있으면 음성 칸의 `없음`을 고를 수 없다 — 영상만 받는 조합은 두지 않는다.

**근거**

- 강의는 음성만, 외국어 영상은 자막만 받는 것처럼 필요한 것만 받을 수 있다.
- `youtube-kit`이 음성·자막을 따로 받는 함수를 이미 제공한다.

**배제한 대안**

- 영상+음성 필수, 자막만 선택: 음성만 받으려면 다른 도구를 써야 하므로 배제한다.
- 영상+음성 필수에 음성만 모드 추가: 자막만 받을 수 없으므로 배제한다.
- 영상만(음성 없음) 받는 조합 허용: `youtube-kit`의 `video()`는 음성을 반드시 함께 받고 영상만 받는 함수가 없으므로 배제한다.
- 영상만 받는 조합을 위해 `youtube-kit`에 기능 추가: 이번 앱의 범위 밖에서 `youtube-kit`을 바꿔야 하므로 배제한다.

---

## D-18 · 해상도 선택지에 fps를 함께 표시

**선택**

해상도 선택지를 `1080p60`, `1080p30`처럼 fps와 함께 표시한다. 해상도·fps·코덱이 같은데도 포맷이 여러 개면(예: 확장자만 다름) 크기가 작은 쪽을 자동으로 고르지 않고 `1080p60 · mp4` / `1080p60 · webm`처럼 모두 보여 사용자가 고른다.

**근거**

- 실제 조회 결과에서 같은 해상도·코덱의 포맷이 여러 개 나온다(예: 1080p vp9가 fps 차이로 2개). 해상도·코덱만으로는 포맷 ID 하나로 정해지지 않는다.
- 열을 늘리지 않고 해상도 칸 안에서 구분한다.

**배제한 대안**

- fps 열을 따로 둠: 열이 늘고 세 칸의 조합 유효성(FR-9)을 맞추기가 더 복잡해지므로 배제한다.
- 해상도·코덱 칸 대신 포맷 목록 하나: 목록이 길고 BRIEF의 "해상도·코덱 선택" 표현과 달라지므로 배제한다.

---

## D-19 · 크기를 하나라도 모르면 `—`로 표시

**선택**

행의 크기는 선택한 영상·음성 포맷의 크기를 모두 알 때만 합계로 표시하고, 하나라도 모르면 `—`로 표시한다. 다운로드가 시작되면 진행 이벤트의 전체 바이트 값으로 채운다.

**근거**

- 실제 조회 결과에서 영상 포맷 크기가 없는 경우가 많다(샘플 29개 중 11개).
- 일부만 더한 값은 실제보다 작은 크기로 오해될 수 있다.

**배제한 대안**

- 아는 부분만 표시(예: `≥ 3.6 MB`): "최소값"이라는 뜻이 표시만으로 전달되지 않을 수 있으므로 배제한다.
- 크기 열을 두지 않음: BRIEF가 행에서 크기를 확인하기를 요구하므로 배제한다.

---

## D-20 · 자막 목록은 수동 자막·원어 자동 자막·선호 언어 자동 번역만 표시

**선택**

자막 선택 목록에는 수동 자막, 원어 자동 자막, 선호 언어의 자동 번역 자막만 표시한다. 선호 언어의 초기값은 한국어(`ko`)이며 설정에서 바꿀 수 있다.

**근거**

- 실제 조회 결과에서 자막 트랙이 150개를 넘으며 대부분 자동 번역이다. 테이블 안 compact 컨트롤에 전부 넣기 어렵다.
- 외국어 영상에서 한국어 자동 번역 자막을 받을 수 있다.

**배제한 대안**

- 수동 자막 + 원어 자동 자막만: 외국어 영상의 한국어 자동 번역을 받을 수 없으므로 배제한다.
- 전부 표시하고 검색: 테이블 안 compact 컨트롤로는 무거우므로 배제한다.

---

## D-21 · `watch?v=…&list=…` URL은 영상 1개로 처리

**선택**

영상 ID와 재생목록 ID가 함께 있는 URL은 영상 1개로 처리한다. 재생목록 전체는 `/playlist?list=` URL로 넣는다.

**근거**

- `youtube-kit`의 현재 URL 해석과 같아 동작이 예측 가능하고 `youtube-kit`을 고칠 필요가 없다.

**배제한 대안**

- 재생목록 전체로 처리: 영상 하나만 원했을 때 수십 행이 생길 수 있으므로 배제한다.
- 그때마다 묻기: "붙여넣기 → 즉시 큐 추가"(D-7)에 한 단계가 끼므로 배제한다.

---

## D-22 · 행 삭제, 전체 정지, 완료 행 지우기 제공

**선택**

선택한 행을 삭제할 수 있고, 받는 중인 행이면 취소한 뒤 삭제한다. 툴바의 정지 조작으로 전체 다운로드를 멈추며 받던 행은 취소된다. 완료된 행을 한꺼번에 지울 수 있다. 취소는 `youtube-kit`의 cancel을 사용하므로 받던 파일이 남지 않는다.

**근거**

- 잘못 넣은 행을 빼고, 받던 작업을 멈출 수 있어야 한다.
- `youtube-kit`이 취소와 부분 파일 정리를 이미 제공한다.

**배제한 대안**

- 행 삭제와 전체 정지만(완료 행은 하나씩 삭제): 재생목록 완료 후 정리가 번거로우므로 배제한다.
- 일시정지·재개(이어받기): `youtube-kit`은 취소 시 받던 파일을 지워 이어받기를 지원하지 않고, `youtube-kit` 변경이 필요하므로 배제한다.

---

## D-23 · 컨테이너는 자동, 자막 형식은 srt, 앱 전체 설정으로 변경

**선택**

영상 컨테이너는 `youtube-kit` 기본값(mp4에 들어가면 mp4, 아니면 mkv)을, 자막 형식은 srt를 쓴다. 둘 다 앱 전체 설정 하나로 바꿀 수 있다.

**근거**

- 대부분의 경우 기본값으로 충분하고, 필요할 때만 설정에서 바꾼다.
- 테이블 열을 늘리지 않는다.

**배제한 대안**

- 행별 선택: 테이블 열이 2개 늘어나므로 배제한다.
- 바꿀 수 없는 고정값: 다른 형식이 필요할 때 방법이 없으므로 배제한다.

---

## D-24 · 여러 줄 붙여넣기 허용, 중복 영상은 건너뜀

**선택**

붙여넣은 내용의 줄마다 URL 하나로 보고 모두 추가한다. 큐에 이미 있는 영상 ID는 추가하지 않고 상태 영역에 건너뛴 개수를 알린다. YouTube URL이 아닌 줄은 행을 만들지 않고 상태 영역에 알린다.

**근거**

- 여러 URL을 한 번에 큐에 넣을 수 있다.
- 같은 영상이 두 번 받아지는 실수를 막는다.

**배제한 대안**

- 중복도 추가: 실수로 같은 영상을 두 번 받게 되므로 배제한다.
- 한 번에 URL 하나만: 여러 URL을 넣을 때 반복 작업이 늘어나므로 배제한다.

---

## D-25 · 설정만 기억하고 큐는 비운 채로 시작

**선택**

앱을 닫았다 열 때 테마·저장 폴더·기본 규칙·선호 언어·컨테이너·자막 형식·창 크기만 기억하고, 큐는 비운 채로 시작한다. 다운로드 중에 닫으면 닫을지 확인하고, 닫으면 받던 작업을 취소한다.

**근거**

- 큐를 복원하면 다시 열 때 정보 재조회와 사라진 포맷 처리가 추가로 필요하다.
- 다운로드 중 실수로 닫는 것을 막는다.

**배제한 대안**

- 설정과 미완료 큐 기억: 재조회와 사라진 포맷 처리가 추가로 필요하므로 배제한다.
- 아무것도 기억하지 않음: 저장 폴더와 테마를 매번 다시 골라야 하므로 배제한다.

---

## D-26 · 정보 조회는 동시 3개, 큐 위에서부터

**선택**

행이 많을 때 정보 조회는 큐 위쪽 행부터 동시에 3개씩 한다.

**근거**

- 재생목록 100개를 1~2분 안에 조회할 수 있다.
- YouTube의 요청 제한에 걸릴 위험이 낮다.

**배제한 대안**

- 한 번에 1개: 100개면 수 분이 걸리므로 배제한다.
- 설정에서 지정: 설정 항목이 늘어나므로 배제한다.

---

## D-27 · 빌드·실행·패키징은 workbench-kit의 pywebview 갈래 방식을 따른다

**선택**

`workbench-kit`의 pywebview 갈래와 같은 방식으로 만든다 — 화면은 Vite + TypeScript로 빌드하고, 개발 중에는 `npm run start:pywebview`로 실행하며, `npm run package:pywebview`로 PyInstaller 실행 파일 폴더를 만든다. 개발 중에는 로컬 `youtube-kit`을 editable 설치로 참조하고, 실행 파일에는 `youtube-kit`과 `yt-dlp`를 함께 묶는다. `ffmpeg`는 실행 파일에 넣지 않고 PATH에서 찾는다. 실행 파일 패키징은 v0.1 Phase 6에 포함한다.

**근거**

- 사용자가 이미 쓰고 있는 방식이라 빌드·실행·배포 절차가 같다.
- 방식만 따를 뿐 `workbench-kit`의 shell·코드에 의존하지 않으므로 D-3과 맞다.
- 통합 검증을 실제 배포 형태로 할 수 있다.

**배제한 대안**

- `_bin` 런처 + editable 설치로만 실행: 사용자가 workbench-kit의 pywebview 방식을 원하므로 배제한다.
- 실행 파일 패키징을 다음 버전으로 미룸: 사용자가 v0.1에 포함하기로 했으므로 배제한다.
- 패키징을 별도 Phase 7로: Phase 6 통합 검증을 실행 파일로 하므로 같은 Phase에 둔다.

---

## D-28 · 이미 받은 파일은 다시 받지 않고 `이미 있음`으로 완료

**선택**

`youtube-kit`이 같은 파일이 이미 있어 다시 받지 않고 `reused`를 돌려주면, 그 행을 완료와 구분되는 `이미 있음` 상태로 끝낸다. 하단 요약에서는 완료로 센다.

**근거**

- 파일명에 포맷 ID가 들어가므로, 다른 포맷을 고르면 새로 받고 같은 포맷이면 다시 받을 필요가 없다.
- 새로 받은 것과 이미 있던 것을 구분할 수 있다.

**배제한 대안**

- 항상 덮어쓰기: 같은 파일을 불필요하게 다시 받으므로 배제한다.
- 설정에서 고름: 설정 항목이 늘어나므로 배제한다.

---

## D-29 · UI 글자는 영어만, 아이콘은 Codicon만

**선택**

UI에 보이는 모든 글자(레이블·툴팁·상태·알림·대화상자)는 영어로 쓰고 한국어를 쓰지 않는다. YouTube에서 받은 값(영상 제목 등)은 원문 그대로 보인다. 아이콘은 Codicon만 쓰고 이모지·다른 아이콘 세트·유니코드 기호를 아이콘 대신 쓰지 않는다. 툴바는 아이콘과 툴팁만 두고, 레이블은 한두 단어, 상태는 한 단어를 원칙으로 하며, 장식용 테두리·그림자·카드를 두지 않는다.

**근거**

- 사용자가 영어와 Codicon만으로 된 간결하고 깔끔한 UI를 원한다.
- Codicon 이름과 VS Code 계열 영어 용어가 한 체계로 맞아 표기가 일관된다.
- 짧은 레이블은 compact한 테이블 중심 화면(NFR-1)에 맞는다.

**배제한 대안**

- 한국어 UI: 사용자가 원하지 않으므로 배제한다.
- 한국어·영어 전환(다국어): v0.1 범위에 비해 과하므로 배제한다.
- 아이콘 옆에 글자 레이블을 함께 표시: 화면이 길어지고 간결함을 해치므로 배제한다.

---

## D-30 · 글꼴·스타일·테마·아이콘은 workbench-kit pywebview 갈래를 참조

**선택**

글꼴·스타일·테마·아이콘은 로컬 `workbench-kit`의 pywebview 갈래를 참조해 같은 값으로 맞춘다 — 글꼴 스택과 공통 스타일 토큰(`src/style.css`), Light/Dark 테마 색(`src/style.css`의 `[data-theme="light"]`·`[data-theme="dark"]` 블록)과 테마 전환 방식(`src/core/theme.ts`), Codicon 패키지(`@vscode/codicons`). `workbench-kit`의 gray 테마는 가져오지 않는다(D-4). 값을 이 프로젝트로 옮겨 쓰며, `workbench-kit`을 의존성으로 두지 않는다(D-3).

**근거**

- 사용자가 이미 쓰는 앱과 같은 시각 체계를 유지한다.
- 이미 두 테마에서 검증된 값을 쓰므로 가독성 튜닝(NFR-2)을 처음부터 하지 않아도 된다.

**배제한 대안**

- 이 앱만의 글꼴·색 체계를 새로 정함: 튜닝 노력이 들고 사용자의 다른 앱과 어긋나므로 배제한다.
- `workbench-kit`의 스타일 파일을 의존성으로 직접 불러옴: shell과 결합되어 D-3에 어긋나므로 배제한다.
- gray 테마까지 포함: D-4가 Light/Dark 두 개로 정했으므로 배제한다.
